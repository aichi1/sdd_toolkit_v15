# 指摘の登録簿（findings register）

フェーズを横断して**未処理の指摘**を持つ唯一の台帳。`/run-phase` で「このフェーズでは直さない」と
決めた指摘（Suggestion、先送りした専門家の指摘、形式・作法だけの指摘）をここに移す。
`/init-task` 後、最初に指摘を先送りするときにプロジェクトルートへ `findings-register.md` として作る。

> **なぜ要るか**: `outputs/.phase-context.json` の `pending_issues` はフェーズ完了ごとに上書きされる。
> 先送りした指摘がフェーズをまたいで散らばると追えなくなり、再現の文脈も消える。
> 実例（SDD Toolkit で別製品を開発した工程、2026-09）: 先送りした 1 件の古い記述が、待っている間に
> 8 箇所へ複製されていた。

## 線引き（どれをその場で直し、どれをここに溜めるか）

| 種類 | 扱い |
|---|---|
| **出荷される成果物（文書・コード）が事実と違うことを述べている** | **その場で直す**（形式に見えても内容の欠陥。待っている間も正しいこととして読まれ、複製される） |
| 構成の改善・重複の整理・書式・用語・引用位置・見出し番号・検査の追加 | **ここに溜める**。修正サイクルを開かない |

## 書き方の規則

- **1 件 1 セクション**（表にしない。再現手順をコードブロックで持たせるため）
- ID は `P<発見フェーズ>-<連番>`（例: `P03-2`）。`outputs/phase-NN/.metadata.json` は**この ID を参照するだけ**
- **状態は `open` / `closed` / `accepted`（既知の限界として受容）の 3 値のみ**
- **再現手順はそのまま実行できる形で書く**（「後で再現し直せばよい」は数フェーズ後には成り立たない）
- **閉じるときは、閉じたことを示すテストか、コマンドと出力を書く**（「直した」だけでは閉じない）

未処理件数の数え上げ:

```sh
grep -c '^- \*\*状態\*\*: open' findings-register.md
```
