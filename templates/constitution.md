# Constitution — {project_name}

> **このファイルの役割**: プロジェクト固有の**非交渉の原則**を、Validator が機械的に判定できる形で定める。
> 出典: sdd-toolkit-v15 プロジェクト（2026-09-04、Iteration 1-2 のドッグフーディング実証）。

各条項は「**原則**」と「**強制点**（どのコマンド／テストで機械的に確認するか）」をセットで書く。
**強制点を持たない原則は載せない。** 検証できない条項は形骸化する。

## 条項テンプレート

```markdown
## 第N条: {原則の短い名前}

- **原則**: {何を守るか。1-2 文}
- **理由**: {なぜか。過去の失敗経緯があれば 1 文}
- **強制点**: {どのコマンドが違反を検出するか。**実行できるコマンドを書く**}
```

## 実証済みの設計原則（sdd-toolkit-v15 より）

### 1. 強制点は「書いた」だけでは効かない

同プロジェクトでは「強制点として書いたコマンドが実際には機能しない」失敗が**同型で 3 回**起きた。

| 実例 | 何が起きたか |
|------|------------|
| `git diff` に `--binary` がない | バイナリ差分で `git apply --reverse --check` が常に失敗。**強制点が一度も機能していなかった** |
| `.gitattributes` の改行正規化 | 証跡ファイルから CR が 9,659 個失われ、逆適用が壊れた。**証跡を作る仕組みが証跡を壊した** |
| 表のパースがエスケープを無視 | exit code 検査が該当行を**黙って読み飛ばし**、失敗を PASS のまま通した |

> **強制点を書いたら、そのフェーズ内で必ず実行して確かめる。**

### 2. 機械チェック自体を負のテストで検証する

チェックを置くだけでは足りない。**わざと違反する入力**を通し、それが fail になることを確かめる。
判定できない入力を**黙って pass にしない**（`skip` として明示的に区別する）。

### 3. 教訓は条文ではなく機械検査に落とす

同プロジェクトでは改正手続きを **3 回**破った。1 回目の直後に条文へ教訓を書き足したが、
次のフェーズで同じ違反を繰り返した。方式を「条文への追記」から「**検出コマンドを強制点に加える**」に
変えて以降、5 件の改正すべてで手続きを守れている。

### 4. 運用ルールは機械検査できるものだけ格上げする

人間向けの運用ルール（`constraints.md` など）は Validator の判定対象になりにくい。
実測では憲法が validation レポートで 24 回引かれたのに対し、運用ルールは **0 回**だった。
**機械検査できるものだけを憲法へ格上げし、残りは「人間が守るもの。判定対象外」と明示する。**

## 改正手続き

憲法の変更は**仕様変更**として扱う。

1. 矛盾を検出したら Validator が `NEEDS_REVISION` を出し、**オーナーへエスカレーション**する（Builder が独断で条項を曲げない）
2. オーナーが優先順位を決定する（コードを直すか、条項を改正するか）
3. **条文を触る前に**オーナーへ提起し、承認を得てから編集する
4. 改正したら関連ドキュメント（`requirements.md` / `plan.md` / 該当 `SKILL.md`）を**同時に整合**させ、再検証する
5. 改正内容を `docs/CHANGELOG.md` と当該フェーズの `change-report.md` に記録する

> **強制点の修理も改正である。** 「原則文は不変だから」という自己判断で手続きを省略しない。
