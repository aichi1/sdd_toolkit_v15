# Add Feature スキル

`.steering/` ディレクトリに基づいたアドホック機能追加を支援し、tasklist.md の進捗管理を確実に行うスキルです。

## スキルの目的

- ステアリングファイル（requirements.md, design.md, tasklist.md）の作成支援
- SDD 知識ベースを活用した計画策定
- tasklist.md に基づいた段階的な実装管理
- **進捗の自動追跡と tasklist.md 更新の強制**
- 実装完了後の振り返り記録

## /run-phase との関係

- `/run-phase` = フェーズベースの計画済みワークフロー（Builder/Validator パターン、`outputs/` に成果物）
- `/add-feature` = アドホックな機能追加（`.steering/` で管理、Builder/Validator 不要）
- 両者は独立して動作し、互いに干渉しない

## 使用タイミング

1. **計画モード**: ステアリングファイルを作成する時
2. **実装モード**: tasklist.md に従って実装する時
3. **振り返りモード**: 実装完了後の振り返りを記録する時

## モード1: ステアリングファイル作成（計画）

### 目的
新しい機能のためのステアリングファイルを作成します。

### 手順

1. **ステアリングディレクトリの確認**
   ```
   現在の日付を取得し、`.steering/[YYYYMMDD]-[機能名]/` の形式でディレクトリを作成
   ```

2. **プロジェクトコンテキストの収集**
   - `CLAUDE.md` を読み、プロジェクトの全体像を把握する
   - `docs/` ディレクトリ内のドキュメントを確認し、関連する設計思想やアーキテクチャを理解する

3. **SDD 知識ベースの活用**
   - `python3 scripts/generate_context.py` を実行し、過去プロジェクトの類似コンポーネントを検索
   - `python3 scripts/search_knowledge.py [キーワード]` でキーワード検索
   - 検索結果から再利用可能なパターンや知見を抽出

4. **テンプレートからファイル作成**

   以下のテンプレートを読み込み、プレースホルダーを具体的な内容に置き換えてファイルを作成:

   - `.claude/skills/add-feature/templates/requirements.md` → `.steering/[日付]-[機能名]/requirements.md`
   - `.claude/skills/add-feature/templates/design.md` → `.steering/[日付]-[機能名]/design.md`
   - `.claude/skills/add-feature/templates/tasklist.md` → `.steering/[日付]-[機能名]/tasklist.md`

5. **tasklist.md の詳細化**

   requirements.md と design.md に基づいて、tasklist.md を詳細化:
   - 各フェーズのタスクを具体的に記述
   - サブタスクも明確に
   - 実装の順序を明記

## モード2: 実装（最重要）

### ループ開始前の必須ゲート（毎反復・省略不可）

**カウンタをコンテキストではなくディスク（`.loop-state.json`）に持たせる。** `maxTurns` は agent frontmatter 専用で
command + skill の `/add-feature` には効かないため、上限は自分で数えるしかない。「覚えておく」のではなく
「毎回ファイルから読み直す」ことで、コンテキスト圧縮（compact）や要約が起きてもディスク上の数値は変わらない。

1. `.steering/[日付]-[機能名]/.loop-state.json` を Read する（無ければ turn_count=0 で新規作成）
2. turn_count を +1 し、**この時点で** Edit/Write で状態ファイルに書き戻す
   （本文の実装作業より前に行う。書き忘れを防ぐため「タスク実行」より先の独立したステップとする）
3. 次のいずれかに該当すれば、実装作業を一切せずに直ちに停止し `stop-report.md` を書く:
   - turn_count >= 60
   - consecutive_failures >= 3
   - task_retry_counts の値がいずれか >= 2（**分割で生まれたサブタスクは親のカウントを継承**。
     タスク名を変えて再試行上限をリセットする逃げ道を塞ぐため）
   - recent_changes に同一 (file, old, new) の組が 2 件
4. 該当しなければタスクの実行に進む

`.loop-state.json` のスキーマ:
```json
{
  "turn_count": 12,
  "consecutive_failures": 1,
  "task_retry_counts": {"T3": 1, "T3-sub1": 1},
  "recent_changes": [
    {"turn": 10, "file": "src/foo.py", "op": "edit", "old": "<old_string 全文>", "new": "<new_string 全文>"}
  ]
}
```
`recent_changes` は**直近 4 件**のみ保持する。

## 停止条件（すべて明示。1 つでも該当したら停止する）

### 正常終了
- `tasklist.md` の全タスクが `[x]` **かつ** `docs/tech-stack.md` の検証コマンドが exit 0

### 上限による停止
| 上限 | 既定値 | 到達時の動作 |
|------|-------|------------|
| 最大ターン数 | **60（暫定値）** | 停止して報告 |
| 最大連続失敗回数 | **3（暫定値）** | 停止して報告 |
| 同一タスクへの再試行上限 | **2（暫定値）** | そのタスクを `blocked` にして次へ。全タスクが blocked なら停止 |
| ~~トークン予算~~ | — | **停止条件から除外**（オーナー決定 2026-09-03。理由: モデルが自分のトークン使用率を機械的に取得する手段が未確認のため。第8条違反のリスクを避け `turn_count` に一本化する） |

> **上限値はすべて暫定値である**（オーナー決定 2026-09-03）。`/add-feature` の実行トラジェクトリが本プロジェクトに
> 1 件も無いため根拠となる実績が存在しない。Phase 11 で実測後に再検討する。

### サブタスク分割による上限回避の防止
分割で生まれたサブタスクは**親タスクの再試行カウンタを継承する**。`task_id` に親の履歴を紐付け、
独立したカウンタとして扱わない。分割回数そのものは制限しない（正当な分割を妨げないため）。

### ループ検知
**判定は厳密な文字列一致で行う**（「行数」「類似度」のような曖昧な基準は使わない）。
- 判定対象: `Edit` は `(file_path, old_string, new_string)` の完全一致、`Write` は `(file_path, sha256(content))` の一致。
  ツールが実際に受け取る引数そのものを比較するため、モデルが計算を誤る余地がない
- ウィンドウは**直近 4 件**（2 件だと A→B→A→B の往復振動を検知できない。4 件あれば直近 2 回分の同一ペアを照合できる）
- **比較前に改行コードを LF に正規化する**（CRLF/LF の差による偽陰性を防ぐ）
- **停止条件**: `recent_changes` 内に `(file, old, new)` が完全一致する組が 2 件あれば停止

### 停止時の出力（必須）
**必ず `.steering/[日付]-[機能名]/stop-report.md` にファイルとして永続化する**。
チャット出力のみだと、セッション終了・compact 後に失われ「次のセッションの人間」が参照できない。
1. 進捗サマリー（完了 N / 全 M タスク）
2. 未完了タスク一覧と各々の最終状態
3. **原因分析** — 要約ではなく、**直近の失敗のエラーメッセージ・テスト出力を逐語引用する**
4. **次に人がやるべきこと** — 「確認してください」のような曖昧表現は禁止。
   **具体的な選択肢を最低 1 つ**含める（例:「タスク T3 をスキップして継続するか / 実装方針を変えるか」）

### 目的
tasklist.md に従って実装を進め、**進捗を確実にドキュメントに記録**します。

### 重要な原則

**MUST（必須）**:
- tasklist.md を常に開いた状態で実装
- タスク完了時に必ず Edit ツールで `[ ]` → `[x]` に更新
- **tasklist.md の全タスクが完了するまで作業を継続する**（ただし「## 停止条件」のいずれかに該当する場合を除く）
- NEVER: tasklist.md を更新せずに次のタスクに進まない

**NEVER（禁止）**:
- tasklist.md を見ずに実装を進める
- 複数タスクをまとめて更新する（リアルタイムに更新する）
- **「時間の都合により」「別タスクとして実施予定」などの理由でタスクをスキップする**
- **未完了タスク（`[ ]`）を残したまま作業を終了する**（停止条件に該当して停止する場合は例外。その場合は `stop-report.md` に未完了タスクを列挙する）

### タスク完全完了の原則

> **本節は「## 停止条件」の下位にある。** 停止条件のいずれかに該当した場合、本節の「継続」「スキップ禁止」の各項目より**停止条件が優先する**。
> その場合は作業を止め、`.steering/<機能名>/stop-report.md` に理由・未完了タスク・ユーザーへの選択肢を書いて報告する（「## 停止条件 › 停止時の出力」）。
> 本節が禁じているのは**理由なき放置と黙ったままのスキップ**であり、**上限到達やループ検知による報告付きの停止ではない**。

**絶対に守るべきルール**:

1. **tasklist.md の全タスクが完了するまで作業を継続すること**（ただし「## 停止条件」のいずれかに該当する場合を除く）
   - 全てのタスクが `[x]` になるまで実装を継続（ただし「## 停止条件」のいずれかに該当する場合を除く）
   - 「時間がかかりすぎる」「難しい」などの理由でスキップしない
   - 未完了タスクがある状態で振り返りを書かない

2. **タスクスキップは原則禁止**
   - スキップが許可されるのは技術的な理由のみ

3. **タスクが大きすぎる場合の対処法**
   - タスクを小さなサブタスクに分割する
   - 分割したサブタスクを tasklist.md に追加
   - サブタスクを1つずつ完了させる

4. **技術的な理由でタスクが不要になった場合のみスキップ許可**

   以下の技術的理由に該当する場合のみスキップ可能:
   - 実装方針の変更により、機能自体が不要になった
   - アーキテクチャ変更により、別の実装方法に置き換わった
   - 依存関係の変更により、タスクが実行不可能になった

   スキップ手順:
   - tasklist.md に技術的な理由を明記してスキップマークを付ける
   - 例: `- [x] ~~タスク名~~（実装方針変更により不要: 具体的な技術的理由）`
   - 振り返りセクションに変更理由を詳細に記録

### 実装フロー

#### ステップ1: tasklist.md を読み込む

```
Read('.steering/[日付]-[機能名]/tasklist.md')
```

全体のタスク構造を把握し、次に着手すべきタスクを特定する。

#### ステップ2: タスクループ（各タスクで繰り返す）

**2-0. ループ開始前の必須ゲート**（上記「ループ開始前の必須ゲート」を実行。停止条件に該当したら 2-1 以降には進まず停止する）

**2-1. 次のタスクを確認**
```
tasklist.md を読み、次の未完了タスク（`[ ]`）を特定
```

**2-2. 実装を実行**
```
タスクの内容に従って実装
```

**2-3. タスク完了を tasklist.md に記録（必須）**
```
Edit ツールを使って、tasklist.md の該当行を `[ ]` → `[x]` に更新

例:
old_string: "- [ ] StorageService を実装"
new_string: "- [x] StorageService を実装"
```

**2-4. 次のタスクへ**
```
ステップ2-1 に戻る
```

#### ステップ3: 全タスク完了チェック（必須）

**全フェーズの実装完了後、振り返りを書く前に必ず実行**:

1. **tasklist.md を読み込む**
2. **未完了タスク（`[ ]`）がないか確認**
3. **未完了タスクが見つかった場合** → **停止条件に該当していなければ**ステップ2 に戻り実装する。該当していれば停止し `stop-report.md` を書く
4. **全タスク完了を確認できた場合のみ次へ**

### 実装中のセルフチェック

5タスクごとに以下を確認:

- [ ] tasklist.md を最近更新したか？
- [ ] 進捗がドキュメントに反映されているか？
- [ ] ユーザーが tasklist.md を見て進捗が分かるか？

## モード3: 振り返り

### 目的
実装完了後、tasklist.md に振り返りを記録します。

### 手順

1. **tasklist.md を読み込む**
   ```
   Read('.steering/[日付]-[機能名]/tasklist.md')
   ```

2. **振り返り内容を作成**
   - 実装完了日
   - 計画と実績の差分（計画と異なった点）
   - 学んだこと（技術的な学び、プロセス上の改善点）
   - 次回への改善提案

3. **Edit ツールで更新**
   ```
   tasklist.md の「実装後の振り返り」セクションを更新
   ```

4. **ユーザーに報告**
   ```
   「振り返りを tasklist.md に記録しました。内容を確認してください。」
   ```

## トラブルシューティング

### tasklist.md の更新を忘れた場合

1. **即座に更新を実行**: 完了したタスクを特定し、すべて Edit ツールで `[x]` に更新
2. **再発防止**: 次のタスクから確実に更新する

### tasklist.md と実装の乖離

1. **tasklist.md に注釈を追加**: 該当タスクに変更理由を記録
2. **必要に応じて新しいタスクを追加**
3. **design.md も更新**: 設計の変更が大きい場合

## チェックリスト（最重要）

実装前に必ず確認:

- [ ] tasklist.md を読み込んだか？
- [ ] 次のタスクを特定したか？

実装後に必ず確認:

- [ ] タスク完了時に Edit ツールで更新したか？
- [ ] tasklist.md の進捗を確認したか？
- [ ] ユーザーが見て進捗が分かる状態か？

## 重要なリマインダー

**このスキルの最も重要な役割は、tasklist.md の進捗管理を確実に行うことです。**

- **tasklist.md が永続的なドキュメント（ユーザーが見る）**

実装中は常に「ユーザーが tasklist.md を見たときに進捗が分かるか？」を自問してください。
