# clarify — 仕様の曖昧さを解消する

## 目的

解釈が割れると成果物が変わる箇所を、**実装前に**確定させる。

## 停止条件（省略不可）

| 条件 | 上限 | 到達時の動作 |
|------|------|------------|
| **質問数** | **5 問** | 残った曖昧点を列挙して停止 |
| 実行の巡回 | **1 巡** | 質問 → 回答 → 追記 で終わる。繰り返さない |

**上限は実装レベルで守る。** 「5 問程度」ではなく **5 問**である。
6 問目を聞きたくなったら、それは次回の `/clarify` の仕事。

> Phase 04 の教訓（R-08 / C-40）: 上限のないループは、止まらないか、
> 止まったことに気づけない。分割して上限を回避することもしない。

## 手順

### Step 1: 曖昧点の列挙

`docs/` を読み、次の型を探す。

| 型 | 例 |
|----|-----|
| 判定方法のない成功条件 | 「使いやすいこと」（何をもって使いやすいか） |
| 判断基準のない語 | 「適切に」「必要に応じて」「十分な」 |
| 相反する 2 つの記述 | A では必須、B では任意 |
| 範囲の内外が判定できない | 「基本的には対象外」 |
| 存在しないものへの参照 | → これは `/spec-check` の担当 |

### Step 2: 最大 5 問を選ぶ

**影響の大きい順**。「解釈が割れたときに成果物がどれだけ変わるか」で並べる。

聞かないもの: 表記の揺れ、実装の詳細、好みの問題、既に決まっていることの再確認。

### Step 3: 1 回のメッセージで提示

1 問ずつ往復しない。全問を一度に出す。

### Step 4: 追記

- **追記のみ。既存の記述を書き換えない**
- 日付と決定者を明記する
- 該当する要件 ID / 成功条件 ID の**直後**に置く

### Step 5: 追記の検証

```bash
git diff --numstat docs/
```

**削除行が 0 であること**を確認する。0 でなければ既存内容を壊している。

### Step 6: 報告

- 聞いた質問と回答
- 追記した箇所
- **残った曖昧点**（あれば。次回の `/clarify` の入力になる）

## Quality Criteria

- [ ] 質問が**5 問以下**である
- [ ] 1 回のメッセージで全問を提示した（1 問ずつ往復していない）
- [ ] 追記のみで、`git diff --numstat docs/` の削除行が **0**
- [ ] 追記箇所に日付と決定者がある
- [ ] 残った曖昧点を報告した

## Common Pitfalls

- **5 問を超える** → 上限違反。残りは次回に回す
- **既存の記述を書き換える** → 追記のみ。改訂が必要なら注記を追加する形にする
- **曖昧でない箇所を聞く** → 質問数を無駄に消費する
- **1 問ずつ往復する** → 往復が増えるだけで情報量は変わらない
