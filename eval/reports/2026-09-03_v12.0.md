## 2. なぜ v6.4 と同値なのか（最重要）

**Phase 01 Step 2 の git 履歴調査（`outputs/phase-01/changelog-draft.md` §2、課題 C-24）により、v6.4 採点以降ツールキットの実体はほぼ変わっていないことが判明した。**

- git 全 9 コミットのうち最古の `b52a405 first commit`（2026-03-15）が、README v6.1・CHANGELOG v6.0〜v6.5・eval v6.1〜v6.4 を**すでに含んだ状態**で 142 ファイル 18,028 行として追加されている
- 以降 8 コミットのうちツールキット本体の実体変更は **`create-deck.md` 追加（`3dca78a`）と `slide_template.js` 追加（`353115c`）の 2 件のみ**
- **v7〜v11 に相当する git コミットは 0 件**。「v12」は git 上の実体を持たない呼称

したがって「v12.0 = v6.4 と同値」は測定失敗ではなく、**実態を正しく反映した結果**である。

### 意図的に採用しなかった選択肢

新たに文書化した欠陥（C-01〜C-25）を根拠にベースラインを**下げる**ことは技術的には可能だった。しかしそれは v13 以降の改善幅を人為的に大きく見せる方向であり、`eval/SCORING_GUIDE.md` の原則「同じ入力→同じ採点」に反する。**ベースラインは据え置き、代わりに各 score.json の notes に「v13 でその軸を上げるために何が必要か」を先に書いた**（下記 §5）。

## 5. 次の改善仮説（最大 3 つ）と、v13 で点を上げるための条件

### 仮説 1: Validator の実行可能化（Phase 03、C-06）→ robustness
`.claude/agents/validator.md` に Bash を付与し、`.validation/report.md` に `## Executed Verification`（コマンド / exit code / pass-fail 数）を必須化する。

> **v13.0 で T2 robustness を 4→5 にするための条件（先に定める）**
> Bash を付与しただけでは根拠にならない。以下 3 点すべてが必要:
> 1. 検証コマンドが未定義のカテゴリで「該当なし」と「省略」が区別されること
> 2. 検証コマンドが exit≠0 のとき PASS にならないことがテストで示されること
> 3. Validator が成果物を改変していないことがハッシュ照合で示されること

### 仮説 2: 衛生・整合性の回復（Phase 02、C-01/C-02/C-18/C-23）→ maintainability
LF 統一（71 件）、旧カテゴリ名の統一（6 ファイル）、README 全面改訂、`.git/` の Zone.Identifier 除去。

> **v13.0 で maintainability を 3→4 にするための条件**
> アンカー 4 は 3（分割され、修正点が追いやすい）と 5（拡張点が明確、重複が抑制され、変更影響が限定される）の中間。
> S-07（旧カテゴリ名 0 件）と S-08（CRLF 0 件・不要追跡 0 件）の達成に加え、README のコマンド一覧が実ファイルと完全一致していることが必要。

> **correctness は上がらない見込み**: C-02 を解消しても `expected_manifest` は元々 100% 充足していたため。この軸で改善を主張しないこと。

### 仮説 3: `/add-feature` の停止条件化（Phase 04、C-07）→ efficiency / robustness
停止条件・上限（ターン 60 / 連続失敗 3 / 再試行 2）・ループ検知。Phase 01 の調査で agent frontmatter に **`maxTurns`** が実在すると判明したため（`outputs/phase-01/claude-code-capabilities.md` 付録 B）、指示文ではなくエージェント定義で強制できる。

> **注意**: 仕様ゲートや検証義務の追加は手数を増やし `efficiency` を下げうる（K-03、`docs/constitution.md` 第7条）。v13.0 で efficiency が 4.000 を下回った場合は Phase 14 のアブレーションで効果を再検証する。

### safety について
> **Phase 02 で `allowedDomains` を 6 ドメインに縮小しても、それ単独では 3→4 としない。**
> 4 を主張するには `deny` 要素数の非減少と、Validator への Bash 付与（Phase 03）が新たな危険経路を作っていないことの実証が必要。
