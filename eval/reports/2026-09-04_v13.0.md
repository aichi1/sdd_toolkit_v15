## 2. 上がった軸

### robustness 3.333 → 4.333（+1.000）— 最大の改善

v12.0 の減点要因は **C-06** ひとつだった。

> `.claude/agents/validator.md:4` の `tools` は `Read, Glob, Grep` のみで Bash がなく、**検証コマンドを一切実行できない**。同ファイル本文の「ツールアクセス権限」節は `bash_tool` の許可コマンドと使用例を詳述しており、**frontmatter と本文が矛盾している**。3 シナリオすべてで `verification_commands_executed = 0`。
> — `eval/reports/2026-09-03_v12.0.md` §3

**T2_implement 4 → 5**。v12.0 の T2 `score.json` は「安易に 5 を付けないこと」として 3 条件を**先に**課していた。すべて実測で確認した。

| 条件 | 判定 | 実測した根拠 |
|------|------|------------|
| (a) 検証コマンドが未定義のカテゴリで「該当なし」と「省略」が区別される | **達成** | `.claude/skills/run-phase/SKILL.md:230,238` / `docs/io-spec.md:92` |
| (b) exit≠0 のとき PASS にならないことがテストで示される | **達成** | `scripts/test_validate_outputs.py` の `TestExecutedVerificationExitCode` / `TestIntentionalExitMarker` / `TestEscapedPipeInCommand` 計 **11 件が通過** |
| (c) Validator が成果物を改変していないことがハッシュ照合で示される | **達成** | `outputs/phase-03/.validation/report.md`（S-03 条件(c)）、`outputs/phase-04/.validation/report.md` §6（5 ファイルの sha256 が検証前後で一致） |

決め手は **S-03 の対照実験**である。`outputs/phase-03/dryrun/` と `dryrun-fail/` は `src/` とテストが sha256 一致で、差は**意図的に失敗する 1 テストのみ**。Validator はそれぞれ **PASS** と **NEEDS_REVISION** を返した。`dryrun-fail/README.md` に書かれた「意図的な失敗であり実装のバグではない / 修正しないこと」に引きずられていない。

もうひとつの決め手が **C-42 の修正**（Phase 05）である。`check_executed_verification()` は行を `split("|")` で分割しており、Markdown のエスケープ `\|` を解釈しなかった。コマンド欄にパイプを含む行は列がずれ、**exit code 欄が黙って読み飛ばされていた**。

```
| 1 | `head -1 x.csv \| tr -d '\r'` | 1 | 失敗 | log |    ← exit code に 1 と明記
→ executed_verification_exit_code = pass                    ← 素通り
```

Phase 04 の `.validation/report.md` でも **17 行中 3 行**が読み飛ばされていた（実 exit code はいずれも 0 と独立確認済みのため判定自体は健全）。第1条を自己申告から機械強制に移した C-34 の仕組みそのものに穴があったことになる。**機械チェックを置くだけでは足りず、そのチェック自体が正しいことを別途確かめる必要がある**——これは C-30（`.gitattributes` が `patch.diff` を破壊）と同型の失敗である。

**T1_research 3 → 4 / T3_proposal 3 → 4**。両者は実行可能な検証コマンドを持たないカテゴリであり、Bash 付与そのものより「該当なし」と「省略」の区別が効く。T3 の v12.0 `score.json` は名指しで宿題を課していた——「Phase 03 ではこの区別を明示する必要がある」。果たされた。

加えて **C-39**: 既存 hook 2 件（`check-docs-exist.py` / `session-start-info.py`）が不正な stdin で `exit=1` を返し**セッションを止めていた**。R-10「hooks は例外時にセッションを止めない」は v12 から要件として存在したが、**誰もテストしていなかったため誰も気づかなかった**。Phase 04 で新設した `scripts/test_hooks.py` の `TestHooksNeverCrash` が機械的に検出した。現在は 4/4 が exit=0。

5 に届かないのは、検証実行の対照実験が T2 でのみ成立するためである。

> **correctness は上がらない見込み**: C-02 を解消しても `expected_manifest` は元々 100% 充足していたため。**この軸で改善を主張しないこと**。

一方で、v12.0 の T3 `score.json` は correctness の減点要因として C-02 を挙げていた——「`.claude/skills/init-task/SKILL.md:114` が旧カテゴリ名 `technical-proposal` を使用し `templates/team-roster.json` の `internal_proposal` と矛盾。さらに roster に存在しない `network-design` カテゴリの docs 構成まで記載」。これは Phase 02 で解消され、S-07 の grep は **0 件**になった。

correctness のアンカーは「必須成果物が揃い、**整合**」であり、整合性の改善は加点根拠になりうる。**両論あることを認めたうえで据え置いた。** 事前に置いたコミットメントを後から都合よく解釈し始めると、評価の信頼性そのものが失われるからである。この判断は Phase 14 のアブレーションで再検討する。

### completeness 4.000（±0）

シナリオが評価するのはテンプレートが規定する必須セクションの充足度である。Iteration 1 は `templates/skills/*.md` の必須セクションを変更していない。checklist は 3 シナリオとも 4/4 pass（grade A）で v12.0 から不変。

### efficiency 4.000（±0）— 測定不能を測定不能と記録する

Phase 03 は `run-phase` Step 2.3 で検証コマンドの実行を**必須化**した。K-03 と第7条が警告するとおり、これは手数を増やしうる。

しかし **v12.0 の `metrics` は `turns` も `retries` も `"unknown"`** であり、**比較の基準が存在しない**。増えたとも減ったとも言えない。推測で下げることは `SCORING_GUIDE.md`「証拠に基づく。推測で点を上げない」の裏返しの違反にあたるため、据え置いた。

定性的には両方向の力が働いている。**増える側**: 検証コマンドの実行と `## Executed Verification` の記録が全フェーズで必須になった。**減る側**: 壊れたテストを含む成果物が PASS する事故（v12.0 の T2 I3 が抱えていた限界）が起きなくなり、後戻りが減る。

軌跡データ（turns / retries）の取得は **Phase 11**（`/eval` 半自動化）で整備し、効果の切り分けは **Phase 14** のアブレーションで行う。
