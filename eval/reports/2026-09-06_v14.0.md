## 2. 上がった軸

### correctness 4.000 → 5.000（+1.000）— Iteration 2 の唯一かつ想定どおりの改善

v13.0 の据え置き理由は「`eval/reports/2026-09-03_v12.0.md` §5 のコミットメントを守るため」であり、Iteration 2 は
そのコミットメントとは独立に、**§4 仮説1 が先に定めた 3 条件**で判定するという新しい前提を敷いていた。

上表のとおり 3 条件すべてが実測で確認できた。決め手は次の 2 点である。

1. **負のテストが本プロジェクト自身のデータを使う**。`test_real_project_detects_iteration3_requirements` は
   フィクスチャではなく `Path(__file__).resolve().parent.parent`（本リポジトリのルート）に対して `trace_check.py` を実行する。
   これにより「ツールが動く」ことと「ツールが実在の未対応要件を見つける」ことの両方を同時に検証できる。
2. **C-19 型の検出がテストとして固定されている**。`spec_check.py` は当初 3 巡の修正でヒューリスティックを積み重ねて
   Critical 10 件を出し、オーナー決定で許可リスト方式に全面転換した経緯がある（Phase 07。`CLAUDE.md`「Phase 07 の教訓」参照）。
   その転換後も C-19 の実例（`/recap` を検証手段として書いた誤り）を検出できることが `test_c19_recap` として固定されており、
   退行があれば pytest が落ちる。

**5 に届いた理由とアンカーの対応**: rubric のアンカー5「必須成果物が完全に揃い、整合性も高い（矛盾がほぼない）」に対し、
Iteration 2 以前は整合性の検査が Validator の目視（散文の読み取り）に依存していた。Iteration 2 以降は
`spec_check.py`（参照の実在性・要件 ID の重複・欠番）と `trace_check.py`（要件↔SKILL↔outputs の対応・未対応要件・孤立タスク）が
機械的に 0 件を返すことを実行時に確認できる。本プロジェクトの現在の実測値（`python3 scripts/spec_check.py` → 0 件、
`python3 scripts/trace_check.py` → 欠陥 0 件）はこの状態を裏付ける。

**この判断を T1/T2/T3 の全シナリオに一様適用した理由**: correctness のアンカーは「必須成果物が揃い、整合」であり、
v13.0 の score.json でもこの軸は 3 シナリオとも同一の理由・同一の値で扱われてきた（T1=T2=T3=4）。
`trace_check.py` / `spec_check.py` はシナリオのカテゴリ（研究レポート／実装／提案書）を区別せず
プロジェクト全体の docs/requirements.md と参照整合性を検査する仕組みであるため、
特定のシナリオだけに効果が限定される理由がない。したがって 3 シナリオとも 5 とした。
