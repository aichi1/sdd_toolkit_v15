# `/spec-check` 許可リスト —— 説明

> **⚠ このファイルはパーサが読みません。** `scripts/spec_check.py` が読むのは
> **`docs/spec-check-allowlist.json`** だけです。本ファイルは人間向けの説明です。

## なぜ JSON なのか

当初は本ファイルの Markdown の表を許可リストとして読んでいた。
**「ファイル内の 3 列の表」を許可とみなすため、本物の許可と次のものを区別できなかった。**

| 混入したもの | 課題 |
|-------------|------|
| コードフェンス（\`\`\`）内の例示 | Critical #13 |
| 別見出しの「却下した候補」の表 | Critical #16 |
| `~~~` 形式のフェンス | Critical #17 |
| **本ファイル自身の「経緯を説明する表」4 行** | Critical #19 |

最後のものは実際に起きた。方式転換の経緯を説明する `| 巡 | 対処 | 次に開いた穴 |` という表が、
`巡` `1` `2` `3` という名前の許可エントリとして読み込まれていた。

フェンスをスキップしても `~~~` が残り、フェンス外の説明表は原理的に区別できない。
**Markdown はデータ形式として曖昧すぎる。**

オーナー決定（2026-09-05）により **JSON に移した**。

## なぜ許可リスト方式なのか

Phase 07 では当初、参照を 8 分類するヒューリスティック（同じ行の否定語、公式ドメインの URL、
文書レベルの宣言、リスト構造など）で誤検出を抑えようとした。**3 巡の修正で Critical 10 件**。

| 巡 | 対処 | 次に開いた穴 |
|----|------|------------|
| 1 | 行に URL があれば引用 / 冒頭宣言で全行抑止 | 引用符なしで URL / 宣言後に手順で使う |
| 2 | 引用符の位置で判定 / 手順を語彙で判定 | 引用符で囲む / 語彙にない動詞 |
| 3 | 構造（リスト）で判定 | 否定語と指示が同じ行 / 全角記号 + 空白なし |

**自然言語の「指示か記録か」を正規表現で判定しようとしたことが原因**である。

現在の方式:

- 実在する参照 → 報告しない
- Claude Code の組み込みコマンド（固定リスト）→ 報告しない
- **`docs/spec-check-allowlist.json` に明示されているもの** → 報告しない
- **それ以外はすべて報告する**

## エントリの形式

```json
{"ref": "recap", "scope": "docs/requirements.md", "reason": "C-19 の記録"}
```

| フィールド | 意味 |
|-----------|------|
| `ref` | コマンド名（先頭の `/` は不要）またはファイルパス |
| `scope` | `*` または対象パス。**パス境界で照合**（`docs/tech` は `docs/tech2/` を通さない） |
| `reason` | **必須**。空なら無効。黙って通すための追加を防ぐ |

## 追加するときのルール

1. **理由を書く。** 「前方参照」だけでは不十分。いつ・どこで作るのかを書く
2. **`scope` を絞る。** `*` は「その参照が文書全体で記録扱いになる」ときだけ
3. **追加は仕様変更である。** `change-report.md` に記録する
4. **Iteration 2/3 の成果物を作ったら、該当エントリを消す**

## `*` を使ってはいけない例

`/recap` と `/agents` は **Quality Criteria #2/#3 を証明するための文字列そのもの**である。
一度 `scope: "*"` で恒久許可したところ、**新しい文書で手順として書いても検出されなくなった**
（Critical #14）。ツールが、作られた目的の欠陥を検出できなくなる。

**記録が実在するファイルだけに絞ること。**

`docs/spec-check-allowlist.json` を参照。件数は次のコマンドで確認する（**手で書かない**）:
